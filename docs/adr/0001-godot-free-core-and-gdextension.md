# ADR 0001: Godot-независимое ядро и GDExtension-адаптер

- Статус: принято
- Дата: 2026-09-06

## Контекст

Нужна симуляция мира на C++ и визуализация в Godot. Связка должна позволять тестировать и гонять мир без редактора, не форкать движок и не делать игровые ноды источником истины.

## Решение

1. Домен живёт в статической библиотеке `sim_core` без заголовков Godot.
2. Godot подключается только через GDExtension (`sim_godot` + godot-cpp), не через custom module / форк движка.
3. Визуализатор потребляет снимки и отправляет команды; фиксированный тик и интерполяция принадлежат ядру/адаптеру, а не `_process` игровой логики.
4. Headless-контур (`sim_cli`, тесты) собирается без godot-cpp.

## Отклонённые варианты

- **Модуль движка Godot.** Требует сборки Godot из исходников и привязывает релизный цикл симуляции к форку.
- **IPC (сокет, shared memory) как основной канал.** Имеет смысл для выноса симуляции на другую машину, но для локальной визуализации даёт лишнюю сериализацию, рассинхрон и операционную сложность. Снимок уже копируемый — IPC можно добавить поверх, не ломая `sim_core`.
- **Симуляция в GDScript/C#.** Противоречит требованию C++-ядра и усложняет детерминированные тесты без рантайма Godot.
- **Ноды сцены как состояние мира.** Путает lifetime дерева Godot с моделью мира, ломает headless и фиксированный шаг.

## Последствия

- Нужен pin godot-cpp на minor Godot (сейчас 4.5). Обновление движка — отдельное изменение адаптера, не ядра.
- Два контура сборки: всегда `sim_core`; GDExtension опционален.
- GDScript не должен дублировать правила движения. Новые доменные поля сначала появляются в снимке/`World`, потом в `SimEntityState`.
- Загрузка санитайзерной `sim_core` в процесс стокового Godot недопустима (preset `debug` vs `debug-godot`).

## Проверка

- `ctest` и `sim_cli` проходят без каталога `third_party/godot-cpp`.
- После сборки `sim_godot` редактор Godot 4.5+ загружает `godot/bin/sim.gdextension`, в сцене появляются агенты, Space ставит паузу без зависимости от FPS исхода тика.
